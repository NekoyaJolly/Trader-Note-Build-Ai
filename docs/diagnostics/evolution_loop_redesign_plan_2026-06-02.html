2. あるべき設計（コンポーネント別）

2-1. 数値最適化（旧 Mutation の数値部分）= 決定論グリッドへ

現状
  • LLM が「RSI 30→35」のような単発変更を提案。
  • 次世代も同じ値を少し動かす → 重複・無駄。
  • 過学習(カーブフィット)の制御なし。
あるべき
  • analysis-engine に POST /v1/optimize を追加し Backtest.optimize(maximize, method='grid'|'sambo', constraint, max_tries) を呼ぶ。
  • 探索空間（各パラメータの range/step）を渡し、決定論で総当たり/SAMBO 最適化。
  • 探索範囲の決め方（確定）：現在値 ±N% を探索幅とし、その範囲内を型(int/float)に応じた刻みで探索する（int は整数刻み、float は適切な小数刻み）。 DSL に ParameterDef.range があればそれを上限/下限の参考にする。決定論コードで実装（LLM任せにしない）。
  • 過学習ガード：学習期間で最適化 → OOS/ウォークフォワードで検証し、OOS劣化が大きい組は棄却。
  • LLM の役割は「どのパラメータを探索対象にするか」「探索範囲のヒント」だけ（構造判断）。数値最適化はしない。

2-2. Crossover = インジ系統スイープでエッジ探索

現状
  • LLM に「負けを消すフィルタを1つ足して」と依頼。稀・非系統的。
あるべき
  • registry.json の ~20 インジを系統的に1つずつ親戦略へ追加してBT。
  • 判定：負けトレードが減り、勝ちトレードが維持される組み合わせ＝そのインジは当該戦略にエッジあり、として採用。
  • インジ自身のパラメータ問題（Nekoさん 指摘）：追加インジ（例 EMA）も period 等の値を持つ。「誰がいつ決めるか」のネック。 → Crossover も Phase 1 の /v1/optimize を呼べるようにし、有望インジが見つかったらそのインジのパラメータを最適化してエッジを確定する（2段：スイープで候補発見 → 最適化で確定）。
  • 決定論スイープが土台。LLM は候補インジの事前絞り込み（多すぎる場合）に限定。
Mutation と Crossover の関係（確定）：Mutation＝既存戦略の“パラメータ”最適化（構造は変えない）。Crossover＝新しいインジを1つ追加し、その“追加したインジのパラメータだけ”を最適化（既存部分は触らない）。 触る対象が分かれるので重複しない。共通の最適化エンジン（/v1/optimize）を両者が呼ぶ形でOK。

2-3. LLM の役割再定義

LLM は 構造の発見・解釈・学習のみ（原則#3）。具体的には：探索対象パラメータの選定 / 追加インジ候補の事前絞り込み / 世代の学び(GenerationLesson)の言語化。数値最適化・エッジ判定・合否は決定論コード。

2-4. 種 / 起動

  • 種は初回(コールドスタート)のみ注入。population に履歴があれば再注入しない（毎ラン12個の再生成をやめる）。
  • 手動「進化を実行」ボタンを追加（既存 /scheduler/run-* と同パターンで admin endpoint）。自動cronは任意（OFF も選べる）。

2-5. 昇格ゲートの整理（Nekoさん 指摘：ゲートが乱立し条件がバラバラ）

現状、段階ゲートが複数あるが「どこに・どの条件で」あるかが分散し、しきい値も段ごとに不整合。まず棚卸しする。

#ゲート場所現在の条件
G1Surrogate 通過（top-K選抜）surrogateRescuePolicy.isNormalPass / evolutionPromotionThresholds.ts学習PF>1.5 / 検証PF>1.3 / WF<0.3（厳格3条件）。+ Rescue Lane（緩和）で“惜しい”候補も正式BTへ。
G2正式BT 合格（formalBtPassed）EvolutionLoop verifyCandidatesWithFormalBacktestin-sample PF≥1.0 かつ trades≥20 のみ（← G1 より緩い。ここが不整合の中心）。
G3PromotionGate ステージ判定promotionGatePolicy.decidePromotionGateV1formalBtPassed→validation_candidate / 失敗+repairable→repairable / その他 repair_excluded / formal_bt_candidate / parent_eligible / hold。
G4OOS-aware（確証）applyOosAwarePromotionvalidation_candidate + oos_passed/wf_passed → validation_confirmed / 失敗→hold。観測のみ・合否に未強制。
不整合の核心：「確証3条件(1.5/1.3/0.3)」は G1(surrogate=近似) でしか効かず、最終の G2(正式BT) は PF≥1.0 だけ。近似で厳しく・本番で緩いという逆転。さらに G4(OOS/WF) は観測どまり。
統一案（確定方針）
  • 「探索ゲート」と「確証ゲート」の2段に集約。探索ゲート(G1相当)＝多様性を残すため緩め（top-K 選抜）。確証ゲートは必ずコスト込みで評価（G1がコスト未計算で確証3条件を効かせても本番より弱く無意味、という逆転を解消）。
  • 確証ゲートの評価指標を増やす（全てコスト込み・各々に閾値）： PF（プロフィットファクター）／ 勝率 ／ トレード数 ／ 最大ドローダウン ／ シャープレシオ ／ リカバリーファクター。 トレード数の下限は確証側にも必ず入れる（少数サンプルの過信防止）。
  • 本番昇格（ユーザー判断）に必要な情報を1画面に揃える：上記6指標の閾値クリア状況 ＋ ウォークフォワード検証結果 ／ モンテカルロ検証結果 ／ バイ&ホールドとの整合比較。これが「本番に上げてよいか」を人が判断するための最低セット。
  • 各ゲートのしきい値を1ファイルに集約（validationThresholds / evolutionPromotionThresholds を単一の正に）。UI に「今どのゲートにいるか」「各指標が閾値を満たすか」を明示。
  • production への自動昇格は引き続きしない（最終はユーザー承認・Phase 5B）。
既存の部品は揃っている：analysis-engine に /v1/walk-forward・/v1/oos-validation、screening BT が Sharpe/maxDD/recoveryFactor を返却、Monte Carlo / Buy&Hold ツールも存在（FullValidation 経路）。再設計は「これらを確証ゲートとして強制＋UIに集約表示」する話で、計算器を新規発明する必要は小さい。
命名の注意（後日修正）：recoveryFactor と profitFactor が両方「PF」と略され混同している箇所がコード/表示に散見。確証ゲートで両方を並べる前に、略記を分離（例: PF=ProfitFactor / RF=RecoveryFactor）して取り違えを防ぐ。今回は把握のみ、別途修正。

5. ベストプラクティス調査（推奨値・2026-06-02 Web調査）

確証ゲート閾値 —「優秀なEAの最低ライン」基準（全てコスト込み）

指標推奨閾値補足
プロフィットファクター (PF)≥ 1.5（プロ級は 2.0〜5.0）> 5.0 は過学習警告。コスト込みで評価。
シャープレシオ≥ 1.0（>2 で優秀）リスク調整後リターン。
リカバリーファクター≥ 2.0純益 / 最大DD。プロ級ライン。
最大ドローダウン≤ 20%最重要のリスク指標。
トレード数≥ 100（最低でも 50）統計的有意性。365日で 100 に満たなければBT期間を延長して確保（OHLCV は ~20年分取得可）。現状の 20 は緩い。
勝率単独閾値は置かないRR 次第で低勝率でも可。表示し PF と併せて見る。

過学習防止（best practice）

  • ウォークフォワード（rolling/anchored）＋ 触らない OOS を必ず確保（gold standard）。リポジトリに walk_forward.py / OOS あり。
  • 最適化の maximize は raw profit / PF ではなく risk-adjusted（シャープ等）にすると過学習が減る（fitness 選択が結果を大きく左右する）。
  • Deflated Sharpe Ratio (DSR) を活用（確定）：リポジトリに computeDeflatedSharpeRatio（dsr.py）が実装済だが現状は観測ログのみ（EvolutionLoop:898）。これを確証ゲートに昇格させる。
  • PBO・CPCV は未実装 → 今回は見送り（「今あるものを活用」方針）。必要になれば将来追加。
  • モンテカルロでロバスト性、Buy&Hold 整合で「相場に乗っただけ」でないか確認。
  • 経済的合理性（バックテストを参照せず戦略を説明できるか）も red flag チェック。

その他（ご意向で確定）

  • ±N% = まず ±30%（将来プレースホルダ化可）。パラメータ種別で変える：SL/TP / 各インジ期間 / 閾値系で別レンジ（型(int/float)刻みも種別ごと）。
  • 自動cron は既定ON＋手動実行ボタンも用意（選択可能）。
  • Crossover の事前絞り込み：AI が「既存インジと相性の良い候補」を選ぶ → 決定論で「親の負けトレードを除去し勝ちを維持するか」を評価（親の trade list ＋ 各エントリー時点のインジ値）→ /v1/optimize で確定。 ＝人が「チャートにエントリー/クローズを描画→インジを当てて優位性を探す→足して再BT」する流れの決定論版。
数値決定 = すべて確定（2026-06-02）： ±N% = ±30%（種別ごと・将来プレースホルダ化可）／ トレード数下限 = 100（最低50・足りなければ期間延長）／ 過学習 = 既存 DSR をゲート化（PBO・CPCV は見送り）＋ WF/OOS/MC/B&H ／ cron = 既定ON＋手動。 → Phase 1 から実装着手可能。
