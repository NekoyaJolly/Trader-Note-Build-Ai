## 3. 使い方のフロー

### Step 1: 最初の一度だけ
1. `CLAUDE_md_supplement.md` の内容を、既存の `CLAUDE.md` の末尾に追記
2. `docs/design/` ディレクトリに全ファイルを配置
3. 設計書 `DESIGN_DOC_autonomous_trading_architecture.md` を一度通して読む(あなた自身が)

### Step 2: 各フェーズ開始時
Claude Code に新しいセッションを開いて、以下のように発注する:

```
フェーズ1を着手してほしい。

前提として以下を読み込んで:
- CLAUDE.md (プロジェクトルート)
- docs/design/DESIGN_DOC_autonomous_trading_architecture.md (全体設計)
- docs/design/phase_1_specification.md (このフェーズの仕様書)

仕様書の「完了条件」を満たすまで実装してほしい。
範囲外の作業は絶対にしないこと。
不明点があったら必ず私に確認すること。
```

### Step 3: 各フェーズ完了時
Claude Code が完了報告を出したら:

1. 仕様書の「レビュー観点」を見ながらチェック
2. 既存機能が従来通り動くか確認(実際に1サイクル回す)
3. 問題なければ次のフェーズの仕様書を読む
4. 運用観察期間(最低2週間)を挟む

### Step 4: 仕様書の更新
実装中に設計の穴や改善が見つかったら、仕様書に追記する(または次フェーズの仕様書でカバー)。**仕様書は生きたドキュメント**。

## 4. Claude Code への発注のコツ

このドキュメントを作ってる中で、あなた自身が気付いたと思うけど、**Claude Code は曖昧な指示に弱い**。以下を徹底すると事故が減る:

### ❌ 悪い発注例
- 「エージェントを賢くして」
- 「レンズを追加してほしい」
- 「この機能作って、ついでにあっちも直して」

### ⭕ 良い発注例
- 「phase_3_specification.md の仕様を実装してほしい。完了条件を全て満たすまで」
- 「仕様書の『触ってはいけない』リストに載っているファイルは絶対に変更しないこと」
- 「不明点は勝手に決めず、私に聞いてほしい」

### 1セッション1フェーズの原則

**1回の Claude Code セッションで扱うのは1フェーズまで**。フェーズ跨ぎの発注は:
- コンテキストが肥大化して精度が落ちる
- 変更範囲が広がりすぎてレビューできない
- 後戻りが難しくなる

フェーズ完了 → 新セッション → 次フェーズ、のリズムを守る。

### 進捗確認のタイミング

長いフェーズ(フェーズ4、5、6)では途中経過を聞く:
- 「ここまでの実装をサマリーで報告してほしい」
- 「残りの完了条件はどれ?」
- 「今の実装で設計書の原則に反しているところはない?」

Claude Code は走り続けると方向がずれることがある。**定期的な自己確認を促す**。

## 5. 設計ドキュメントの維持管理

### 設計が変わったとき
実装を進める中で「この設計、実はこうした方がいい」と分かることがある。その時は:

1. まず該当フェーズの **運用を止めない**(動いてるものは動かしたまま)
2. `DESIGN_DOC_autonomous_trading_architecture.md` に **判明した事実** を追記
3. 次フェーズ以降の仕様書に **対応方針** を反映
4. 必要なら過去フェーズの成果物を改修(その場合も新たに phase_N_revision.md として仕様化する)

### 未実装項目のトラッキング
全フェーズ完了後も、やり残しは必ず出る。以下をプロジェクトの Issue として管理:
- 拡張アイデア(「こういうレンズも欲しい」)
- 改善アイデア(「ここのスコアリング関数を見直したい」)
- 発見されたバグ・挙動の癖

これらは新たなフェーズ or マイクロフェーズとして順次仕様化する。

## 6. このアーキテクチャの核心を忘れないために

実装を進める中で細部に埋もれると忘れがちなので、再掲する:

### 6.1 設計哲学 6原則

1. 優先順位ではなく、判断品質のメタルールを与える
2. レンズは排他選択ではなく並列計算
3. LLMに期待することを限定する
4. 検証可能性を絶対に捨てない
5. 人間との共通言語を維持する
6. 勝ちを急がない

### 6.2 積み上げ順序は交換不可能

柱2(レンズ基盤) → 柱1(エージェント) → 柱3(進化ループ)。この順でないと後続が成立しない。

### 6.3 既存を壊さない

新機能は常にラッパーか拡張として足す。後方互換を維持する。UIを止めない。

### 6.4 勝ちではなく台帳の成長を主指標にする

短期的に勝つ戦略より、検証済みエッジが台帳に積み上がることのほうが重要。
