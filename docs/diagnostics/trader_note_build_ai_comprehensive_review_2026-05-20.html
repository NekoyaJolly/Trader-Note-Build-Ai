3.2 具体的改善提案

APIクライアントを Zod 検証付きにする

src/frontend/lib/api.ts は巨大化しており、response.json() 後に optional chaining と型アサーションで整形する箇所が多いです。API境界では次のような共通ヘルパーを導入してください。

import { z } from "zod";

const ApiErrorSchema = z.object({ error: z.string().optional() }).passthrough();

export async function fetchJson<T>(url: string, schema: z.ZodSchema<T>, init?: RequestInit): Promise<T> {
  const response = await fetch(url, init);
  const raw = await response.json().catch(() => null);
  if (!response.ok) {
    const parsedError = ApiErrorSchema.safeParse(raw);
    throw new Error(parsedError.success && parsedError.data.error ? parsedError.data.error : `HTTP ${response.status}`);
  }
  const parsed = schema.safeParse(raw);
  if (!parsed.success) {
    throw new Error(`APIレスポンス形式が不正です: ${parsed.error.message}`);
  }
  return parsed.data;
}

localStorage token fallback の本番無効化

  • 本番では httpOnly Cookie のみを認証ソースにする。
  • 開発環境のクロスオリジン fallback は NODE_ENV !== 'production' か明示 feature flag でのみ有効化。
  • CSP を導入し、inline script を避ける。Next.js middleware または hosting layer で Content-Security-Policy を付与。

Server Components / data fetching 戦略

現在トップページは "use client" のワークベンチに寄せています。認証必須・リアルタイムUIが多い点は妥当ですが、静的な説明、設定メタデータ、初期一覧などは Server Component / Route Handler / cache strategy を分けると Core Web Vitals を改善できます。

状態管理

  • サーバー状態: TanStack Query または SWR で取得・再試行・キャッシュ・invalidations を統一。
  • クライアント状態: Auth / UI preference / chart session を小さな Zustand store に分割。
  • リアルタイム: SSE/WebSocket の接続状態を専用 hook + store 化し、再接続/backoff を標準化。

4. Node.js / Express バックエンドレビュー

4.1 現状分析

  • 構造: src/app.ts は Express routes を集約し、backend/api、services、repositories、side-b/jobs に分かれています。Side-B scheduler は Job 分割済みで、以前の巨大クラスから改善されています。
  • 入力検証: cTrader 認証ルートなどでは Zod を使用しており、規約と方向性が一致しています。
  • 非同期処理: Scheduler + setInterval が中心。BullMQ は依存に存在しますが、コード検索では Queue/Worker の実利用が見当たりませんでした。
  • エラーハンドリング: グローバル Express error handler は存在。ただし route ごとの try/catch が多く、例外形・エラーコードが統一されていません。
  • 運用: cron/scheduler がアプリプロセス内で動くため、水平スケール時の二重実行リスクがあります。

4.2 改善提案

項目提案理由
セキュリティ middlewarehelmet、rate limit、body size limit、CORS origin 監査ログの構造化を追加。OAuth・取引口座連携を扱うため、一般Webアプリより強い防御が必要です。
Job 実行基盤BullMQ を本格導入し、Plan/Monitor/Evolution/Validation を Queue 化。Redis lock / jobId で冪等化。setInterval は単一プロセス前提。Cloud Run 等で複数インスタンス化すると重複実行します。
エラー標準化AppError、errorCode、details、requestId を統一。Zod error も同じ envelope に整形。FE/AIオーケストレーションが失敗原因を機械判読しやすくなります。
ログconsole.log から pino/winston + JSON logging に移行。runId/jobId/userId を付与。現在は人間可読ログが多く、横断トレースには弱いです。
Lint OOMESLint を backend/side-b/shared などに分割し、CIでは matrix 実行。型情報 lint は対象を絞る。現状 npm run lint:backend がヒープ不足で失敗します。

5. Python / FastAPI analysis-engine レビュー

5.1 現状分析

  • FastAPI: analysis-engine/app/main.py に /health、/v1/walk-forward、/v1/oos-validation、/v1/screening-backtest、/v1/indicator-series などがあります。
  • Pydantic v2: field_validator、model_validator を用いて bool / NaN / Infinity / params 整合を検証しており良好です。
  • DB: SQLAlchemy Engine を module load 時に生成。Read-only 前提のコメントがあり、pool_pre_ping も設定済み。
  • 同期処理: FastAPI endpoint は def 同期関数。pandas/backtesting.py のCPU処理が多いため同期自体は悪くありませんが、Uvicorn worker/thread 設計が重要です。
  • 型: Python側は Any や柔軟 dict が残ります。JSON/DSL互換性を優先した結果ですが、境界を schema に閉じ込める設計は維持すべきです。

5.2 改善提案

  • FastAPI の dependency injection で engine を注入し、テスト時に差し替え可能にする。
  • CPU重い backtesting / pandas 計算は別 worker process または Celery/RQ/BullMQ 経由に分離し、HTTP request timeout と切り離す。
  • 例外ハンドラーを追加し、validation_error、insufficient_data、engine_error を機械判読可能な JSON に統一する。
  • ANALYSIS_DATABASE_URL は read-only DB user を必須化し、アプリ起動時に SHOW transaction_read_only 相当をチェックする。
  • pytest で Pydantic schema、indicator-series、OOS validation、DB無し unit を拡充。現状の python/ stdlib walk-forward と analysis-engine/ の二重構成は役割整理が必要です。

  • インデックス: 多くの時系列・status・symbol に index が付与され、基本的な検索性能は意識されています。

7. AIエージェントループ設計レビュー

7.1 PDCALoop

src/side-b/agent/pdcaLoop.ts は IDLE → SESSION_OPEN → MONITORING → EVALUATING_ENTRY → MANAGING_POSITION → REFLECTING → REVISING_STRATEGY の状態機械を持ち、ThinkingLogEntry で内部状態を記録しています。

観点評価コメント
自律性中状態遷移はあるが、実際の Research/Plan 実行は SideBScheduler に委譲。PDCA 自体は意思決定エンジンというより状態ログ・スケジューリング補助に近いです。
回復性良tick 例外時に通常間隔でリトライし、lastError を保持します。
可視性良ThinkingLogEntry は有用。ただし永続化されず、プロセス再起動で失われます。
拡張性中setTimeout 単一ループのため、マルチシンボル・複数 agent run の並行管理には RunLedger との統合が必要です。

7.2 EvolutionLoop

このコードベースで最も設計密度が高い領域です。良い点は以下です。

  • Surrogate fitness と正式 BT を明確に分離し、surrogate だけで昇格しない。
  • Surrogate Rescue Lane により normal pass が 0 の世代でも、near miss / low DD / trade count / novelty を正式BT候補へ回せる。
  • analysis-engine を評価正本とし、OOS verdict を Evolution 側で再判定しない方針が明記・実装されています。
  • RepairHint、RepairOutcomeTelemetry、Adaptive Repair Budget、Quality-Diversity Archive Lite により、自己改善ループの部品が揃っています。
  • GenerationReflectionAgent と GenerationLesson 永続化により、人間語 lesson を次世代へ持ち越す設計があります。

10. 結論

Trader-Note-Build-Ai は、単なる取引ノートアプリではなく、検証可能なAI戦略探索基盤へ進化しているコードベースです。特に Side-B の EvolutionLoop は、Surrogate 評価、正式BT、OOS、RepairHint、世代間学習、プロンプト進化を組み合わせた高度な設計で、最新の自己進化型・モジュラー型エージェント設計に近い水準にあります。

一方で、本番運用の信頼性という観点では、認証 token の扱い、OAuth token 暗号化、Express security middleware、job queue 化、RLS policy、FE runtime validation が次のボトルネックです。短期ではセキュリティと品質ゲートを先に固め、中期で RunLedger/BullMQ/ADK tracing によってAIオーケストレーションを観測可能・再実行可能にすることを推奨します。
