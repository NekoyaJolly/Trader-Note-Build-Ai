Trader-Note-Build-Ai コードベースレビュー

Side-B 重点レビュー。テーマは「各 AI エージェントが生成した根拠・エビデンスが、どこまでユーザー (UI) に届いているか」。エージェント出力 → DB 永続化 → API レスポンス → フロント描画の 4 層を端から端まで追跡し、根拠が消失している地点を特定した。結論: 根拠の生成は非常に豊かだが、永続化と描画の 2 段で大量に脱落している。

主要な良い点

  • 各エージェントは極めて豊かな根拠を生成している。推論テキスト系フィールドは全エージェント合計で 65+ 個 (Research の reasoning.{trendAnalysis,momentumAnalysis,…}、PlanAI の scenarios[].rationale / reasonForSelection / multipleTestingDefense、BullBear の bull/bear.rationale[] / synthesis.reasoning / phaseAnalysis 等)。「ブラックボックスを作らない」ドメイン原則 §6 はエージェント層では守られている。
  • 仮説詳細 (HypothesisDetail.tsx) と AI ノート (ai-notes/page.tsx) は根拠表示の良い手本。採用/棄却理由・改善提案・entry/exit 評価・learnings を丁寧に描画している。これを他画面に展開すれば良い。
  • API 層はおおむね素直で、DB に保存されている根拠は意図的に握り潰している箇所はほぼ無い (Prisma の JSON 列をそのまま返している)。つまりボトルネックは API ではない。
  • EdgeHypothesis / ResearchOutput / AITradeNote は根拠保存が手厚い (interpretation 系テキスト・learnings・各種 evaluation を専用列 or JSON で保持)。

P1 Frontend (仮説一覧) 仮説一覧カードに statusNote / confirmationNote が出ず、状態変化の理由が一覧では追えない (詳細を開くまで分からない)。 HypothesisCard.tsx は statement/メトリクスのみ。statusNote 未使用。 カードに statusNote の 1 行サマリを追加 (詳細リンクは維持)。
P1 観測性 (RunLedger) AgentRun / Step は redaction 済み summary のみで、各ステップの中間根拠を保持しない。これは設計上の意図 (raw 非保存) だが、UI から「この plan がどのエージェント経路で出来たか」を辿れない。 schema.prisma AgentRun の comment に「raw prompt / raw output は保存しない」と明記。 raw は保存せず、構造化サマリ (各 step の confidence / 採用方向 / 主要根拠 1 行) を残す方針を別途検討。
P2 一貫性 根拠の返却フォーマットが画面ごとにバラバラ (VirtualTrade.reflection は生 JSON、Reflections は整形済み、thinking-log.reasoning は PDCA 状態レベルでトレード根拠ではない)。 API 調査: sideBController.ts の各 reflection 返却が不統一。 「根拠ペイロード」の共通型・共通描画コンポーネントを 1 つ用意して横展開。
一言で: 根拠が消える地点は 2 つ。(A) 永続化で消える = Debate と Indicator 分析は保存すらされない (LLM 課金が無駄になっている)。(B) 描画で消える = プランの根拠フィールドは保存・返却されているのに画面が描かない。トレードで一番大事な「なぜこのプランか」は、ちょうどこの 2 つの穴に落ちている。

8. AI Agent / Side-B (`src/side-b/`)

8.1 PDCALoop

状態機械として安定。thinking-log は action + 任意 reasoning を記録するが、reasoning はセッション/ループの状態遷移レベル (「監視継続」「決済完了」等) で、個別プランの根拠ではない点に注意。デフォルト enabled:false、本番は cron 駆動。

8.2 EvolutionLoop

Discovery (組成役・日次・feedback loop) / Mutation (インジ最適化) / Crossover (インジ追加でエッジ発見) の役割が確定。Discovery の weeklyNote / lensInsights[].interpretation / hintsForHG[].rationale など豊かな根拠を出すが、UI 露出は funnel/lessons レベルに留まる。

8.3 AI オーケストレーション

generatePlan の経路: Research(or cache) → Lens 計算 → EdgeLedger マッチ → IndicatorSpecialist (LLM) → PlanAI (LLM) → BullBearDebate (LLM) → debate で scenario 方向調整 → 永続化。豊かな根拠を 3 つの LLM が生成しているのに、永続化されるのは PlanAI 出力 (marketAnalysis/scenarios) だけ。IndicatorSpecialist と Debate の固有出力は §7 の通り脱落する。これが「エージェント出力のほとんどが UI に出てこない」の構造的原因。

8.4 観測性 (ADK trace / RunLedger)

各 LLM ステップは tracePlanStep で trace されるが、RunLedger は redaction 済み summary のみ保存 (設計上 raw 非保存)。結果として「どのエージェントが何を根拠に寄与したか」を後から UI で再構成できない。§7 P2 の構造化サマリ案で部分的に解決可能。

9. テスト / CI

Side-B のテストは 141 ファイルと厚め。レンズの決定性テスト・各ジョブのテストが整備されている。ただし「根拠フィールドが永続化 → API → 描画まで届くか」の end-to-end テストは手薄 (今回のギャップはユニットテストでは検出されない種類)。根拠サーフェシング改修時は、保存→取得→レスポンスにフィールドが残ることを検証するテストを追加すべき。CI は tsc + ESLint (no-any/no-unknown) + Jest が PR ゲート。

11. まとめ

Nekoさんの体感「各エージェントの出力がほとんど UI に出てこない」は正確で、原因は 2 段階に分解できた:

  • (A) 永続化で消える — BullBearDebate と IndicatorSpecialist の出力は LLM が生成・課金しているのに AITradePlan に保存列が無く、生成直後の一瞬しか存在しない。最も損失が大きい (トークンを払って捨てている)。
  • (B) 描画で消える — プランの根拠 (additionalInsights / macro / MTF / reasonForSelection / indicatorsIgnored / multipleTestingDefense 等) は保存も API 返却もされているのに、フロントが描いていない。最も直しやすい (フロント作業のみ)。

救いは、エージェント生成は既に A 級で、手本となる描画 (HypothesisDetail / ai-notes) も既にあること。やることは「新しく賢くする」ではなく「既に生成・保存している根拠を、消さずに最後まで運ぶ」配管工事。トレードの納得性 = 「なぜ」の可視化に直結する、費用対効果の高い改善である。

推奨着手順: (1) AITradePlan へ debate/indicatorAnalysis のオプショナル列追加 (要 migration 承認) → (2) 既存返却済みフィールドのプラン描画 → (3) debate/indicator のプラン描画 → (4) 共通化と一覧カード。各ステップは独立 PR 可能。
